# Mooncake 冷层接入 Us3Turbo 方案

> 一篇介绍：为什么把 Us3Turbo 对象存储接入 Mooncake KVCache 引擎，以及接入后承担什么作用。
> 面向未读过源码的读者；实现与构建细节见文末指针。

## 1. 背景：Mooncake 与 KV cache

Mooncake 是面向 LLM 服务的分布式 KVCache 存储引擎（FAST'25 Best Paper）。它要解决的问题是：大模型生成每个 token 时，都要回看此前所有 token 的"注意力记忆"——这部分张量称为 **KV cache**。

以接力会议作类比：每位发言人留下两叠笔记卡——一叠"标签卡"（K）供他人按主题检索，一叠"内容卡"（V）是其发言实质。下一位发言人以自己的"提问卡"（Q）检索所有历史标签卡，按相关度加权混合对应的内容卡，据此决定下一句表述。每新增一位发言人，都需用到**此前所有人的卡片**，故这些卡片不可丢失——丢失则需从头重开会议。

在大模型中，"从头重开会议"即**重算 prefill**：将 prompt 中所有 token 重新过一遍神经网络、重新计算其 K/V 张量。该过程消耗 GPU 算力、耗时数秒，期间 GPU 无法处理其他任务。因此 KV cache 本质是 **prefill 阶段 GPU 算力的凝结产物**——保留即省算力，丢失则需重算。

单 token 的 KV 体积很小：`2 × 层数 × KV头数 × 头维度 × 字节数`，8B 模型约 128 KiB/token、70B 约 320 KiB/token。但一段长上下文含数千至数万 token，累积后单个 prefix 的 KV 即达 1~10 GB——这正是其"高价值、大体积"特征的来源：丢失代价高（重算成本高），全部保留于 GPU/内存又容量不足。

Mooncake 的解法是**分层存储**：热数据置于 GPU/内存（称为 segment），满后**下沉**至更廉价的冷层（offload）；下次使用时再**回填**热层（promotion）。该"空间换时间"机制使有限的高速介质仅承载最热数据，温冷数据流向廉价介质、按需取回——既不丢失，又不挤占热层。

## 2. 痛点：冷层是本地盘，规模不足

Mooncake 当前冷层为**节点本地 NVMe**（若干文件/块后端实现）。机制本身合理，但介质规模受限：

- **节点失效即数据丢失**：本地盘与节点同生命周期。autoscaler 缩容、硬件维护、节点崩溃，盘上 KV 随之丢失——而这些在云上属常态。idle 用户的高价值 prefix 随节点回收全部丢失。
- **idle 大 prefix 被驱逐后只能重算**：一个 70B×32k 约 10GB 的 prefix，重算 prefill 耗时数秒且**独占 GPU**。当服务正处理其他请求时，GPU 被重算占用，吞吐直接受损。
- **不跨集群**：A 集群计算好的 prefix，B 集群无法复用。全局 prefix 缓存、跨区调度、follow-the-sun 容量调度均无法实现——而这些恰是规模化服务的诉求。
- **容量受单盘限制**：长上下文 × 多用户，单机 NVMe 的 TB 级很快用尽；HBM/内存更小。容量满后只能丢弃，丢弃则触发上述重算。
- **数据与进程生命周期强绑定**：用户隔天续用会话时，本地盘 KV 已随节点失效而丢失——跨会话恢复无法实现。

概言之，Mooncake 具备"下沉→回填"的空间换时间机制，但冷层缺少一层 **持久、跨集群、可扩容**的远端存储。本地 NVMe 是"低延迟但节点本地"的介质，所缺的是"延迟较高但跨集群存活、容量近无限"的一层。

## 3. 方案与接入：用 Us3Turbo 补一层 durable 冷层

### 3.1 为什么是对象存储，为什么是 Us3Turbo

对象存储恰好补足缺失的层次：数据落到后端对象存储即**跨节点、跨集群、跨重启存活**，容量近无限（PB 级）、单价远低于本地 NVMe。其延迟较高，但冷层数据本不要求低延迟——要求的是"持久保存、按需取回"。

选 Us3Turbo 而非普通 S3 的原因：Us3Turbo 是 **GDS+RDMA 双通路**对象存储，使数据**不绕经主机**直达后端：

- **CPU 上的产物走 RDMA**：内存中的 KV，后端直接经 RDMA 读取。
- **GPU 显存上的产物走 GDS**：显存中的 KV，后端直接读取 GPU 显存。

传统持久化链路为 `GPU → 主机内存 → 本地文件 → 再上传对象存储`，需三跳、且产生临时本地文件。Us3Turbo 双通路将其简化为一次操作：数据一次写入即落定对象存储，**不经主机内存中转、不落本地文件**。对 GPU 上的 KV 价值尤为显著——省去 GPU↔host 的 PCIe 往返与中间落盘。

### 3.2 整体数据流

Us3Turbo 接入为 Mooncake 冷层的一个新后端，挂于本地 NVMe 之外，作**最外层 durable 冷层**：

```
GPU/内存(热, segment) ──下沉──► 本地 NVMe(低延迟但节点本地) ──溢出/镜像──► Us3Turbo 对象存储(持久冷层)
   ▲                                                                              │
   └────────────── 回填（网络拉取，不占 GPU）──────────────────────────────────┘
```

下沉（offload）：Mooncake 从热层驱逐一个对象时，不丢弃，而是落到 Us3Turbo。
回填（promotion）：Mooncake 下次使用该对象时，从 Us3Turbo 拉回热层——拉取为网络密集型、**不占 GPU**，期间 GPU 仍可服务其他请求。

### 3.3 怎么接：一个适配器连通两套系统

无需改动 Mooncake 核心，亦无需改动 Us3Turbo——在两者之间增设一个**适配器**：它实现 Mooncake 的冷层抽象接口（Mooncake 内部为 `StorageBackendInterface`），内部调用 Us3Turbo 的对象存储客户端。承担三件事：

- **下沉一个对象** → 适配器将其写为 Us3Turbo 的一个对象（PUT）。
- **回填一个对象** → 适配器从 Us3Turbo 读回（GET），数据直接写入 Mooncake 预分配的缓冲区。
- **查询对象是否存在** → 适配器向 Us3Turbo 查询。

### 3.4 粒度：一个 prefix = 一个对象

一个 Mooncake 对象（通常是一段 prefix 的 KV cache）对应**一个 Us3Turbo 对象**；大对象以分段上传（multipart）拼接。

为何不按 KV cache 内部更小的分片（slice）切分？因如此将产生海量小对象，每个小对象均需一次控制面 RPC 与建链开销，控制面开销急剧上升，且违背对象存储不宜过小的特性。故选 1:1 聚合——slice 是 Mooncake 内部的分片细节，对 Us3Turbo 透明；一个逻辑 prefix 对外即一个对象、一个 key。

### 3.5 挂在哪一层：级联或镜像

Us3Turbo 挂于本地 NVMe 之外，两种可选（待下一阶段选定）：

- **三级级联**：本地盘用尽后才溢出至 Us3Turbo。Us3Turbo 作最冷层，本地盘仍为快路径。
- **持久镜像**：offload 至本地盘的同时，异步镜像一份至 Us3Turbo。本地盘快路径不变，节点失效后 Us3Turbo 仍保存数据，可从镜像重建。

两者均不改动 Mooncake 既有的"下沉/回填"主链——仅替换/补充冷层后端。

## 4. 优势与不足

### 优势

- **idle 会话恢复**：KV 下沉至持久介质，下次按需回填，免重算 prefill——以空间换 GPU 时间，正对应"1-10G 闲置结果被丢弃、下次续用"场景的解法。
- **节点/集群回收不丢失**：数据跨节点、跨重启、跨集群存活，autoscaler、维护、崩溃均不受影响。
- **跨集群共享**：A 集群计算的 prefix，B 集群可直接拉取，支持全局 prefix 缓存与跨区调度。
- **容量可扩**：本地盘 TB 级，对象存储 PB 级廉价冷池，容量满则溢出、不丢失。
- **省 GPU（吞吐净增）**：回填为网络密集型、不占 GPU；重算则独占 GPU。即便耗时相当，回填期间 GPU 仍可服务其他请求，吞吐净增。
- **GPU 直送持久**：GDS 通路使 GPU 上的 KV 一次落定对象存储，省去 `GPU→host→本地文件→再上传` 的中转。
- **成本**：显存 > 内存 > NVMe > 对象存储（$/GB），高价值但低频访问的数据置于最廉价介质，经济合理。

### 不足 / 边界

- **延迟地板高，仅适合冷层**：对象存储为 ms~s 级，热 KV 必须留存内存；它不抢占热层，而是热层容量不足时的下沉去处。
- **回填需算经济账**：仅当"重算 > 回填"才有收益。长 prefix（1-10G、重算数秒）有收益；短 prefix 重算比回填更快，不宜存储。
- **缺删除/枚举**：Us3Turbo 客户端暂无 Delete/List，对应接口现为空操作——接入真实驱逐、需清理对象前需补齐。
- **接入有摩擦**：两项目的日志库冲突、参数对齐等工程细节（已解决，详见实现文档）。
